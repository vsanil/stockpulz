## Memory / OOM architecture (settled Jun 12, 2026 — do not relitigate)

- **Render 512MB CANNOT run the 600-ticker screener in any form** — full agent.py OOMs, thin run_prescreener.py OOMs. Proven empirically 5+ times. Do not try again.
- **Prescreener runs on GitHub Actions** (7GB): daily_run.yml schedules 03:00 UTC primary + 07:00 UTC backup, both → prescreener mode. Cache save is idempotent.
- **Render /trigger/prescreener is a relay** — dispatches the GH workflow via GITHUB_TOKEN; never spawns locally. cron-job.org keeps hitting it unchanged (redundant third trigger).
- **`_can_run_live_screener()` guard in agent.py**: morning run NEVER falls back to the live screener when RENDER env var is set (Render sets it automatically). Cache miss → admin-only alert + crypto/ETF picks continue; users see normal "no stock setups today" rendering.
- **Morning DELIVERY also relays to GitHub Actions (FIXED Jul 1, 2026).** The old belief "morning run WITH cache is light, well under 512MB" was FALSIFIED — even with the cache, run_morning (ETF screen + Claude analysis w/ per-ticker sentiment + signal cache + personalised send) OOMs Render's 512MB. Symptom: `cron_last_morning` updates daily (process starts, sets it) but `last_morning_run` + `picks._saved_date` freeze (killed mid-run, before save_picks), and the per-day guard then blocks retries → users silently get NO morning picks for days. Render logged "Ran out of memory (used over 512MB)" at 11:01 UTC. Fix: `webhook.trigger_morning` now RELAYS to GH Actions (dispatches daily_run.yml `run_mode=morning`, mirrors /trigger/prescreener) instead of `subprocess.Popen(agent.py)`. **Rule: any run that does screening/Claude/ETF work must execute on GH Actions (7GB), never spawn on Render — Render only relays + serves the web/API.** NOTE: deliberately did NOT add a GH `0 11 * * 1-5` schedule cron — that would race the cron-job.org relay and double-send (delivery isn't idempotent, unlike the prescreener cache). `force=true` propagates through the relay → daily_run.yml `force` input → `FORCE_MORNING` env for recovery.
- **🔴 The SATURDAY path was never converted — fixed Aug 15, 2026.** `run_weekly_recap` opens with `run_morning(config, now_et)` ("Saturday: run crypto morning picks, then send a compact weekly recap"), so `/trigger/weekly` was running the FULL morning pipeline locally on Render through the generic `/trigger/<mode>` `subprocess.Popen` path — the exact thing the Jul 1 fix removed from the weekday path. It had run that way every Saturday since.
  - **Symptom it produced, and how it hid: the run "succeeds" but sets ZERO auto alerts.** Sat 2026-08-15 generated and DELIVERED GLD + SLV, and neither real user got a single alert — while the identical code yields `GLD stop@381.41` + `SLV invalidation@49.71` when run anywhere else. `_auto_set_pick_alerts` catches per-ticker, so every failure logged and continued and `last_morning_run` stamped normally. Weekday mornings (GH Actions) alert correctly; only the Render-executed Saturday run did not. Prime suspect: `add_alert` → `_current_price` failing from Render's IP. **Confirming it needs Render logs — there is still no `RENDER_API_KEY` in `.env`.**
  - Fix: dedicated `webhook.trigger_weekly` relaying via the new **`webhook._relay_to_github(mode, force, tag)`**, with its own `cron_last_weekly` guard and `?force=true` bypass. The static route wins over `/trigger/<mode>`, same as morning/prescreener. **`trigger_morning`/`trigger_prescreener` keep their inlined copies deliberately** — morning delivery is the highest-risk path in the app; migrate them only when there is another reason to touch them.
  - **Rule restated: grep `run_morning(` before assuming the weekday path is the only one.** There are exactly TWO callers (`mode == "morning"` and `run_weekly_recap`); `tests/test_api.py::TestOnlyWeeklyAndMorningReachRunMorning` fails if a third appears. Sunday's `run_week_ahead` is safe — "No new picks are generated" — asserted by test rather than assumed.
  - **Method lesson: I checked ONE execution surface (GitHub Actions), saw no `daily_run`, and reported "nothing ran today".** Render is a second surface. The `cron_last_*` / `last_morning_run` stamps in the config are the authoritative record of what actually executed across both — read those first.
- To confirm a morning-path change without spamming users: reproduce run_morning locally with `requests.post`/`requests.patch` stubbed (blocks ALL Telegram sends + Gist writes) and `_screener_cache_with_retry` stubbed to the real cache — it runs the full path read-only. (This is how the Jul 1 OOM was proven to be environmental, not a code bug.)
- Manual cache recovery: `python3 run_prescreener.py` locally, or `/trigger/prescreener?secret=…&force=true`. Manual morning recovery: `/trigger/morning?secret=…&force=true` (relays to GH with FORCE_MORNING).
- An unmapped schedule in daily_run.yml defaults to prescreener, NEVER morning — must not send user-facing picks at odd hours.

### Bug pattern: function-local datetime imports + bulk refactors
- The Jun 8 utcnow() cleanup replaced `datetime.utcnow()` → `datetime.now(timezone.utc)` but missed adding `timezone` to FUNCTION-LOCAL `from datetime import …` lines in config_manager.py. ### Bug pattern: function-local import SHADOWS a module-level name → UnboundLocalError (Jul 3, 8 bugs)
- A name imported at module level (e.g. `os`, `get_user_config`, `_fetch_live_price`, `load_user_trade_log`, `update_user_config`) that is ALSO re-imported *inside* a function becomes **local to that entire function** (Python binds it for the whole scope). Any code path that uses the name BEFORE the local import line raises `UnboundLocalError` — swallowed by the command catch-all into "⚠️ Something went wrong", so it looks like a transient glitch, not a bug. It only fires on the branch that reaches the early use, so it hides for months.
- The full_sweep (Jul 3) found 8 of these live: `/positions /history /dashboard /missed` (cmd_trades `import csv, io, os` at the /export branch shadowed module `os`), `/size` (cmd_market local `from cmd_helpers import _fetch_live_price`), the **no-picks morning broadcast** (agent `run_morning` — every user's "no setups today" send silently failed), `run_confirmation`, `_handle_pending_reply`, `handle_callback_query`, `_cmd_admin`, `_cmd_settings`.
- **Fix pattern: DELETE the redundant function-local import** (the name is already module-level). Only keep a local import for names that are NOT module-level (e.g. cmd_settings kept `load_user_trade_log`, cmd_admin kept `save_user_trade_log`).
- **Guard: `tests/test_no_shadow_imports.py`** does a scope-aware AST scan of every project `.py` and FAILS on any use-before-local-import where the name is module-level. Keep it at zero. **Rule: never re-import a module-level name inside a function — if you need it, it's already imported; a local re-import is a latent UnboundLocalError.** `py_compile` does NOT catch this (runtime error); only the AST scan / a test that actually calls the command does.

### Bug pattern: price-fetch failures must never reach price logic (Jun 23)
- **Non-positive price = failed fetch, never a real quote.** yfinance `fast_info.last_price` can return `0.0` or `nan` on a bad/exotic symbol (e.g. HYPE). `if price:` rejects 0/None but **`nan` is truthy** — it slips through. A `$0.00` price made every "below" alert fire ("HYPE is now $0.00", because `0.00 <= target`). Guard with `price and price > 0` at EVERY return point in `_current_price`, AND at the trigger site (`price_alert_manager.py` check_alerts: skip `current is None or current <= 0`). Defense in depth — guard at both the source and the consumer.

### Bug pattern: `> 0` is NOT enough — tiny-positive garbage on a market holiday (Jul 3, sequel to Jun 23)
- The Jun 23 guard (`price > 0` / `<= 0`) was under-generalised: it fixed the exact symptom (`$0.00`) not the class. On the **Jul 3 US-holiday** the feed returned tiny POSITIVE garbage — **TSLA `$0.01`, UNI/WEN/SHOP ~`$0.004`** (displays `$0.00`) — which passes `> 0` and then trivially satisfies any "below $X" target → a cascade of false "now $0.00 · −100%" alerts, a false EOD `▼100% stop hit`, a false `🔴 STOP HIT` sell nudge, and a collapsed portfolio total that made two positions each read "49% of your portfolio". Fired live while the canary was green (nothing injected a bad price).
- **Fix = validate against a REFERENCE, not just `> 0`.** `market_data.plausible_price(price, reference, lo=0.1, hi=10.0)` — the ONE class-level guard: rejects None/NaN/≤0 AND anything outside `[reference*0.1, reference*10]` (a >90% collapse / >10x spike between checks is a bad fetch). Reference = the price we last knew for real: an alert's `price_at_set` (fallback `target`), a position's `entry`. Applied at the notification/headline paths: `price_alert_manager.check_alerts`, `formatters` EOD `_row` + the portfolio-P&L aggregate loop, `agent._check_portfolio_health` (implausible → fall back to entry/cost-basis, so no false concentration/nudge), `agent._check_hold_or_fold` (no false STOP-HIT sell signal).
- **Rule: any NEW code that compares a live price to a stop/target/entry, or leads a P&L number, must gate on `plausible_price(price, reference)` — never a bare `> 0` / `_is_pos`.** Guard/regression: `TestImplausiblePriceGuard` (alerts), `TestEODImplausiblePriceGuard` (EOD), `TestPlausiblePrice` (unit), and canary `check_price_guard` (injects `$0.01`, keeps the monitor honest). **🔴 THIS WAS DECLARED "FULLY CLOSED (Jul 6)" AND WAS NOT — four more live sites were found on Aug 19** (`_check_take_profit_nudge`, `_check_trailing_stops`, `_check_picks_stop_loss`, `_check_portfolio_drawdown`), every one of them on an alert that tells a user to act. The Jul 6 sweep looked for the sites it could remember; it never enumerated them. **Do not write "fully closed" for a bug CLASS unless a scan enumerates every site mechanically and it is kept as a test.** What Jul 6 actually closed was the display-only sites: the last display-only sites — pre-market card crypto row + stock row + the watchlist "moving X% today" move-alert — also gate on `plausible_price` (crypto/stock vs entry-or-prev-close; move vs previous close). No known consumer of a live price still uses a bare `> 0`/`if price` on a stop/target/entry/P&L path.
- **Crypto needs the `-USD` suffix in EVERY yfinance call that takes user tickers.** A bare `yf.download("BTC")` resolves to an unrelated ~$28 instrument, not BTC-USD (~$27k). The Jun 8 sweep converted "all 5 yf.download calls" but **missed the watchlist big-move check** (agent.py) → BTC priced at $28. Fixed by extracting `_yf_symbol_map(tickers)` (BTC→BTC-USD via `_SYMBOL_TO_CG_ID`) and routing the move-check through it. **Rule: any new `yf.download`/`yf.Ticker` on watchlist/position/user tickers MUST go through `_yf_symbol_map` or `_download_prices` — never raw `" ".join(tickers)`.** Note: position card uses `_download_prices` (correct); only standalone download sites are at risk.

### More single sources of truth (second audit, Jun 26)
- **Dates: `config_manager.et_today()` (US/Eastern date) for ALL dedup keys, idempotency guards, date stamps, and day-diffs.** Bare `date.today()` is UTC on Render → rolls over at 7-8 PM ET, so evening alerts double-fired/suppressed and date stamps were off by one. Ranged historical lookbacks may stay on `date.today()`. **Rule: any new dedup key / date stamp / "days held" uses `et_today()`.**

### Walk-forward backtest — `scripts/backtest_walkforward.py` (Aug 12)
- **Why**: the live evaluator needs ~1,500 picks (~1 year) to separate a 55% engine from a 60% one. Replaying history is the only honest way to get thousands of samples quickly — **and the most common way retail systems fool themselves**, so the discipline is the feature, not the code.
- **TRAIN window: tune freely. HOLDOUT: `--holdout`, ONE SHOT.** Every view is appended to `.holdout_views.json` and printed back ("HOLDOUT VIEWED N times"). After the first look it is no longer out-of-sample, and any number it produces afterwards is a lie you told yourself.
- **🔴 What it CANNOT test, and why — restate these with any number it prints:**
  - **Long-term score is EXCLUDED.** Finnhub serves CURRENT fundamentals only, so scoring a 2024 pick with 2026 P/E is look-ahead. Excluded rather than faked.
  - **Claude's selection is NOT replayed** — expensive, and the model's training contains the outcome. This measures the SCREENER RANKING, which is the part with tunable weights anyway.
  - **Survivorship**: uses TODAY's universe, so dead/delisted names are missing and any edge is an **optimistic upper bound**.
- **The baseline is the point.** A win rate alone is unreadable. Each date also scores the MID-RANKED candidates from the same eligible pool, so the question is "do top-ranked beat mid-ranked", not "did picks make money". `EDGE < 3 points` prints as *within noise*.
- Forward scoring matches the live evaluator exactly: **stop checked BEFORE target on the same bar** (conservative — a both-touched bar is a loss, and those are the volatile days), else mark-to-market at 30 days. Entry is the decision bar's close; forward window starts at the NEXT bar. Guard: `tests/test_backtest_walkforward.py` pins the stop-before-target rule, the no-look-ahead slice, the stop clamp, and that Wilson stays honestly wide at small n.
- **🔴 FIRST REAL RESULT (Aug 12, TRAIN window, n=510 over 2 years / 298 tickers / 67 rebalances): NO DETECTABLE EDGE.** Top-ranked picks won **44.3%** [CI 38.3–50.5]; mid-ranked baseline from the same pool won **45.9%** [39.9–52.0]. Edge **−1.6 points — within noise**. Survivorship bias makes this an optimistic bound, and even so the technical score does not rank better than arbitrary selection from the eligible pool.
  - **This is failure-to-detect, NOT proof of no edge.** At n=255/bucket the CI is ±6 points, so a real 3–5 point edge would not reliably show. It does mean the ST rubric's weights are unlikely to be where the value is — **tuning them further is low-expected-value until something shows a signal**.
  - **Untested and still open**: the LT fundamentals leg (not point-in-time) and Claude's final selection. Neither is condemned by this.
- **🔴 The harness caught ME first, and that is the lesson worth keeping.** Run 1 used the CONFIG defaults (15% target / 1.5×ATR ≈ 3.9% stop = 3.8:1) and produced a confident, wrong headline: 59% stop-outs vs 10% targets, "the levels are broken". Real ledger picks are **10.3% / 5.5% = 1.9:1**. A wider target with a tighter stop manufactures stop-outs. With measured levels the mix went 150/26 → 103/52 and the "finding" evaporated. **Rule: a backtest's assumptions must be measured from what users ACTUALLY got, never read off config defaults.** Guard: `test_default_levels_match_MEASURED_reality_not_config_defaults`.
  - Note which conclusion survived: the **edge** number moved −3.5 → −1.6 (both noise) because picked and baseline share whatever levels are used, while the **absolute** win rate moved 34.9% → 44.3%. Comparative claims are robust to that error; absolute ones are not.
- Bars cached to `scripts/.backtest_bars.pkl` (`--refresh` to refetch). Compute scales as tickers × rebalances; use `--limit` / `--step`.

### Proposed-change gate — `scripts/backtest_compare.py` (Aug 14)
- **The fast half of "keep trading, keep improving".** Live learning runs at ~6 independent observations/weekday × a 30-day horizon ≈ one usable verdict a year, and every engine change resets the ledger's meaning so the count restarts. This answers the same question against 2 years of history in minutes: `proposed change → backtest vs default → adopt / reject / not conclusive`. Cheap and reversible in front of expensive and irreversible; survivors go to a live A/B arm, losers never touch a user.
- **🔴 The head-to-head is scored on DISAGREEMENT ONLY.** Two strategies over the same dates mostly pick the same names, and shared picks have IDENTICAL outcomes by construction — counting them drags both win rates together and manufactures "no difference" no matter how far apart the strategies are. Total agreement reports NOT CONCLUSIVE ("there is not enough disagreement to measure"), never a confident `0.0` edge. Guard: `TestDisagreementOnly`.
- **Rules are INHERITED from `backtest_walkforward`, never re-implemented** — bars, `score_forward`, stop-before-target, MIN_BARS, and the measured levels (10.3%/5.5%). A guard asserts `def score_forward` does not appear in the compare script; a forked scoring rule would let a comparison silently use different rules than the single-strategy report.
- **TRAIN only — the holdout is deliberately unreachable from this script** (no `--holdout` flag, no `HOLDOUT_LOG` import). Comparing candidates IS tuning, and the holdout is spent the first time it is looked at. Guard: `test_the_holdout_is_unreachable_from_this_script`.
- **Verdict is hard to pass on purpose**: `MIN_N = 30` disagreeing picks *per side* (matches `evaluate_picks._MIN_N` and `performance_context._MIN_DIRECTIVE_N`), plus a 95% CI on the difference that must exclude zero. A win prints "run a live A/B arm before shipping" — **a backtest win is never permission to ship.**
- **CI is Newcombe's hybrid-score method, not Wald.** Wald's variance term collapses at p≈1, so a 12-for-12 arm would get a ZERO-WIDTH interval and the harness would certify a decisive win from twelve observations. Guard: `test_a_perfect_arm_does_not_collapse_the_interval`. (Near p=0.5 the two are comparable — the extremes are the failure mode. An earlier version of this note claimed Wald fails at 0.5; that was wrong.)
- **🔴 FIRST RUN (Aug 14, TRAIN, 298 tickers / 51 rebalances) — the A/B arms overlap far more than their names suggest.** `breakout` shares **44%** of its picks with `default`; `pullback` shares **63%**. Neither separates (`+2.1` pts CI [−9.4, +13.5]; `+1.1` pts CI [−12.9, +15.0]). All three strategies land 44–46% and each still *loses* to its own mid-ranked baseline (−1.6, −1.6, −6.3 pts), consistent with the Aug 12 no-detectable-edge result.
  - **This directly weakens the case for the A/B arms cron.** `test_arms_actually_disagree` requires ≥8/12 differing **SCORES** — but differing scores are not differing **PICKS**. At 63% overlap a live arm spends most of its budget measuring identical picks, so it would need roughly 3× the samples to detect anything. **Do not schedule `ab_arms.yml` on the strength of the arms "being far apart" — measure pick overlap first.**
- Usage: `python3 scripts/backtest_compare.py [names…] [--baseline default] [--limit N] [--step D]`. Defaults to every registered strategy.

### Bug pattern: read-after-write LAG defeats the merge → cross-user lost update (Aug 3, FIXED)
- The batch-3 protections above are NOT sufficient on their own. The per-file lock serializes our own writes and `read_strict` raises on fetch errors — but **neither protects against GitHub's read-after-write lag**: a fresh `GET` moments after a `PATCH` can still return the PRE-write copy. That stale copy then becomes the merge base for the NEXT user's write, silently erasing the previous one.
- **Observed live**: tagging the owner's 34 trades then the test account's 4 (two `_update_user_keyed_file` calls, different uids, ~1s apart) left the owner's tags **completely gone** while the test account's persisted. Nothing errored.

Costs **no extra network calls**. `_WRITE_ECHO_TTL = 30s` — deliberately tight so a genuinely newer write from another process (GH Actions) isn't stomped once the echo expires.
- **Rule: any read-modify-write against the Gist must assume the read may be one write stale.** Guard: `tests/test_storage_lost_update.py` uses a `_LaggyGist` whose reads lag one write behind — verified it FAILS without the fix (2 failed) and passes with it. ### Supabase migration — row-per-user storage (Aug 3, BUILT + DORMANT)
- **Why**: the Gist can only rewrite a WHOLE file, so saving one user rewrites the blob every other user shares. That is the root of both storage data-loss classes, and it is unfixable there — the Gist API has **no compare-and-swap** (verified: `PATCH` with `If-Match` returns **400** for a valid OR wrong ETag; only conditional READS work).
- **Schema** (`supabase_schema.sql`, run once in the SQL editor): `documents` (whole-blob files) + `user_records` (**one row per user**, `primary key (filename, chat_id)`, with a `version` column) + `upsert_user_record()` which returns NULL on version mismatch = **true CAS**.
- **Backend**: `storage.SupabaseBackend` gained `supports_rows()/read_user/write_user/read_all_users` + a non-swallowing `read_strict`. `config_manager` now resolves through `get_storage_backend()` — **it previously hardcoded `GistBackend()` everywhere, so the documented "upgrade path" was dead code and setting the env vars did nothing.**
- **`config_manager.USER_KEYED_FILES`** lists the chat_id-keyed files that become rows. `_load_gist_file` reassembles `{chat_id: record}` from rows so every existing caller is unchanged.
- **DORMANT until `SUPABASE_URL` + `SUPABASE_KEY` are set** — with them unset `get_storage_backend()` returns `GistBackend`, `supports_rows()` is False, and every path is byte-identical to before (verified: 715 tests green, dormancy asserted).
- **Migration**: `scripts/migrate_to_supabase.py` (`--dry-run` first). READ-ONLY on the Gist, verifies every doc/row by reading back, and refuses to run without the env vars. **Rollback = unset the env vars** (the Gist is never modified).
- **`mutate_gist_file` is ALSO row-aware** — required, not optional. `price_alerts.json` is USER-KEYED but `add_alert`/`remove_alert` go through `mutate_gist_file`; on a row backend that would have written the whole-blob `documents` table while readers reassembled from `user_records` rows — alerts written to one place, read from another, **silently broken on switchover and green in every Gist-based test**. It now reassembles rows, runs the mutator on the familiar `{chat_id: value}` mapping, and persists only the rows that changed. Guard: `TestMutateGistFileIsRowAware`.
- **Rule: any NEW per-user read-modify-write must use `mutate_user_record`** — on rows it retries the mutator on a CAS conflict instead of clobbering; on the Gist it still shrinks the window.

### Same-user CROSS-PROCESS race → use `mutate_user_record` (Aug 3, partially fixed)
- **There is NO server-side compare-and-swap on Gists.** Verified empirically: `PATCH` with `If-Match` returns **400 whether the ETag is valid or wrong**; only conditional READS work (`If-None-Match` → 304). So optimistic locking is impossible at the API level.
- **The racy pattern** is `log = load_user_trade_log(uid)` … seconds of work (price fetches, LLM calls) … `save_user_trade_log(uid, log)`. Another PROCESS (a GitHub-Actions job) writing the same user in that window is silently clobbered. This is real, not theoretical — scheduled jobs write real users' trade logs (`agent.py:1971, 3254`) and configs (`:3054, :4644`).
- **Fix = `config_manager.mutate_user_record(file, uid, mutator)`** (and the `mutate_user_trade_log` shorthand): the mutator runs on a FRESH read taken microseconds before the write, instead of on a snapshot the caller took earlier. Shrinks the window from seconds to milliseconds. `close_trade` is migrated; guard: `TestSameUserCrossProcessRace`.
- **Rule: any NEW per-user read-modify-write must use `mutate_user_record`, never `load_*` → modify → `save_*`.**
- **RESIDUAL CLOSED (Aug 5)** — the three deferred sites were converted, plus five more found by scanning the same class:

Log AFTER the write lands, never inside the mutator.

### Scale hardening (Jun 28) — what's done vs deliberately deferred
- **Telegram 429 backpressure**: `telegram_api._retry_after_secs(resp)` reads `parameters.retry_after` (then the `Retry-After` header, capped 30s) and all 4 send paths (send_message, send_inline_keyboard, send_photo, async broadcast_all) sleep that long on 429 instead of the fixed RETRY_DELAY. **Rule: a new send path must handle 429 via `_retry_after_secs`, not a blind fixed retry.**
- **OHLCV cache**: `market_data.get_ohlcv` caches per `(ticker, days)` for `_OHLCV_TTL` (600s). Safe because chart callers fetch the live price separately — cached *historical bars* never stale a quote. Don't cache live-price functions this way (violates "live price always trumps stale").
- **Webhook dedup**: `webhook._is_duplicate_update(update_id)` (bounded in-process dict) drops Telegram retries of an already-handled update — prevents double position-logs / double replies when a slow handler (LLM) doesn't ack fast.
- **DEFERRED (not done, by design)**: full async-webhook backgrounding (ack-then-dispatch-in-thread) and converting the serial `for uid in _all_recipients(): send_message()` broadcast loops in agent.py to `broadcast_all`. At ~2 users these give ~no benefit and carry real regression risk on the core request path / live delivery; the `update_id` dedup already fixes the double-processing that backgrounding would. Revisit with load testing as concurrent users grow (the morning picks loop already uses `broadcast_all` as the template).

### Bug pattern: "NEAR STOP" must not mask a blown-through stop (Jul 2)

### Bug pattern: overlapping backtest entries inflate N (Jul 1)
- `miniapp_backtest_pick` counted EVERY day within 2% of entry as a separate sim, so a stock that hovered near the entry level for 10 days produced ~10 overlapping "trades" from one real setup — inflating both wins and losses and making win rates look far more statistically robust than the handful of independent setups behind them (AMBA showed 0/21 that was really 0/3 distinct episodes).
- Fix: NON-OVERLAPPING trades — each entry starts one trade, then the scan skips to `exit_idx + 1` (past the target/stop hit, or past the 60-day window) so consecutive days of the same setup aren't re-counted. **Rule: any historical-simulation/backtest that scans a price series must advance past each trade's exit, never count overlapping entries — N must reflect independent trials.**

### Units & user-data hygiene (release polish, Jun 28)
- **Screener stop fields are PERCENTS, not fractions.** `screener.py` writes `atr_pct = atr/price*100` and `suggested_stop_pct = atr_pct*1.5` as percents (e.g. 7.5 == 7.5%). `position_sizer` needs a 0-1 fraction, so it normalizes via `_as_fraction(v)` (`v/100 if v>1 else v`). Before the fix every ATR-fallback stop was clamped to `_MAX_STOP_PCT` (0.20). **Rule: any consumer of `atr_pct`/`suggested_stop_pct` must normalize — don't assume a fraction.**

So a null stop on an LT pick is BY DESIGN, not missing data. **Rule: render a null stop neutrally** (mini-app pick card: gray "— no stop" for LT, NOT a red `$—` which reads as broken); never backfill a stop onto a long-term pick. ### Money is not a price — `formatters._money()` (Aug 15)
- **`_p()` is the PRICE formatter**: magnitude-keyed, dropping to 4–8 decimals below $1 so sub-penny crypto renders honestly. It was also being used for MONEY, which put **`risk $0.9600/share`** in the live morning message where `$0.96` was meant. **Rule: `_p()` for prices, `_money()` for risk / P&L / totals.**
- `_money()` is 2 decimals with thousands grouping, and keeps going below a cent rather than rounding to `$0.00` — a sub-penny coin's per-unit risk genuinely IS a fraction of a cent, and showing a real non-zero amount as zero is the same class of lie `_is_pos`/`plausible_price` exist to prevent. None/NaN/inf render `—`.
- **Found a live gap underneath it: the risk was pre-rounded with `round(e - stop, 2)`.** On a sub-penny coin that becomes `0.00`, fails the `if risk_per_share > 0` guard, and **silently drops the ENTIRE risk + position-sizing line** — for exactly the picks where sizing matters most. - Guard: `TestMoneyIsNotFormattedLikeAPrice` + `TestSubPennyRiskLineNoLongerVanishes` — 8 of 10 verified failing against the reverted code, incl. that `_p()` keeps its sub-dollar precision (the skip-above level on the same line depends on it).

### Serial delivery loops — `agent._fanout()` (Aug 19)
- **At 2 users a `for uid in _all_recipients(): send_message(...)` loop is invisible; at 100 it is the delivery model.** Telegram allows ~30 msg/s, so a serial loop is ~35s of wall clock per broadcast — and it is worse than slow: `send_message` RETRIES on a 429, so one throttled user **blocks every user behind them**, and the failure lands on whoever is late in the list. `broadcast_all` (asyncio + aiohttp, 30-way semaphore) already existed and was used by exactly one caller.
- **`agent._fanout(msg_for, recipients=None, tag=...)`** — builds every message first, then sends them in ONE `broadcast_all`. `msg_for(uid)` returns a string, a dict (`{"text":…, "keyboard":…}`), or **`None` to skip that user** (paused, nothing to say). Returns the number that landed.
- **The per-user try/except is INSIDE the helper, not optional** — the pre-existing rule "one user's failure can never abort delivery for the rest" is preserved by construction, and a build failure now skips that user instead of the whole loop. Failed SENDS are logged with the tag rather than swallowed; `broadcast_all` returns `{chat_id: ok}` and nobody was reading it.
- **Converted so far: `run_vix_check`, `run_monthly_commentary`, the `run_morning` week-ahead block.** Guard: `tests/test_fanout_delivery.py` (11 tests, incl. that an empty outbox makes NO API call and that the guard itself fails when a site is reverted).
- **Second batch (Aug 19): 8 more converted** — `run_confirmation` ×3 (confirmation message, earnings warnings, watchlist signals), `run_macro_alert_check`, `run_pre_earnings_guidance`, `run_monthly_pnl_digest`, `_check_trade_reminders`, `run_week_ahead`, the weekly missed-picks digest, and `run_price_alerts`' watchlist-move block. `_fanout` now also accepts a **LIST** of messages for a user who gets N of them, and **returns USERS reached, never messages** — `broadcast_all` keys its result by `chat_id`, so N messages to one user collapse to one key and counting messages off it would silently under-report. Ordering within one user's batch is not guaranteed, so only pass a list where the messages are independent (different tickers).
- **Where per-user NETWORK work exists it stays in the BUILD phase** (`get_upcoming_earnings`, `yf.download`, `yf.Ticker().info`, `_watch_move_quote`). The build is still serial; the SENDS fan out. That is the honest win — do not claim the network cost went away. Dedup marks (`_mark_alerted`, `cache_set`) also stay in the build, exactly as before, so semantics are unchanged.
- **`_check_trade_reminders` clears reminders AFTER the fan-out, not during the build** — clearing during the build would drop a reminder whose send then failed.
- **`_broadcast_trade_closes` is DEAD CODE** — it `return`s on its second line (auto-close removed per user preference). Its conversion is a no-op; `test_dead_code_is_not_counted_as_converted` pins that so nobody counts it as live delivery.
- **🔴 7 of the 9 converted functions had ZERO test coverage — a green suite said NOTHING about them.** That matters more here than elsewhere: self_heal auto-merges an LLM's fix gated only on this suite. `TestConvertedSitesActuallyDeliver` now drives each one and asserts a payload reaches `broadcast_all` with its keyboard intact. **Rule: before converting a delivery path, check whether anything tests it — `grep -rl <fn> tests/`.**

### 🔴 OPEN DECISION: `crypto_screener._simple_rsi` uses a NON-STANDARD divisor (found Aug 19)
- It divides the gain sum by the **count of gains**, `statistics.mean(gains)`. **Every other RSI in this repo divides by the PERIOD** — Wilder's standard: `agent.py:3508` (`sum(gains[-period:]) / period`), `agent.py:1114` and `ai_analyzer.py:463` (`delta.clip(lower=0).rolling(14).mean()`). crypto_screener is the odd one out, with no comment claiming a deliberate variant.
- **Measured divergence: on a downtrend containing one spike the two forms give 90.91 vs 43.48.** They agree on monotonic series and disagree on mixed ones — the non-standard form inflates RSI whenever gains are fewer but larger than losses, so a spiky downtrend reads as overbought.
- **It changes pick output.** The value feeds `if rsi and 42 <= rsi <= 62` in `_short_term_score`, the "neutral momentum" band — and that band only means what it is meant to mean under standard RSI.
- **NOT fixed unilaterally**: correcting it changes which crypto picks real users are shown, and `backtest_compare`/`backtest_walkforward` **cannot gate it** — both replay the STOCK screener on daily equity bars and do not touch crypto. So there is no cheap evidence path here; it is a judgement call, and it is the owner's.
- Guard: `tests/test_crypto_screener.py::TestRsiDivergence` asserts the divergence EXISTS rather than that either value is right, so a future refactor cannot silently "clean it up" without the decision being made. **If it is corrected, delete that test and record the decision.**

## Position logging: total-invested is the primary input (settled Jun 15, 2026)

- **Robinhood does dollar-based investing** — users buy "$500 of LRCX" / "$50 of BTC" and receive fractional shares (1.377, 0.0008). They remember the **total invested** and roughly **when**, NOT the per-share price or share count. Designing the Log Position form around per-share price was the root of the LRCX `entry_price=500` bug (a total typed into a price field poisons every %-based P&L and alert).
- **The form has two paths** (`miniapp/index.html` buypos sheet):
  - **Default — "💵 Total invested"**: total $ + buy-date chips (Today/Yesterday/2d/Pick…). Derives `entry_price = close(date)` and `shares = total / close`. Today reuses the live quote; past dates call `/api/miniapp/close_on_date`.
  - **Toggle — "🎯 Exact $/share"**: per-share entry + optional shares. For intraday traders who know their fill.
- **Why two paths, not one smart field**: a single field that accepts both "500 the total" and "362 the price" is ambiguous — that ambiguity WAS the bug. Forcing the user to declare which they mean is the fix.
- **`/api/miniapp/close_on_date?ticker=X&date=YYYY-MM-DD`** (webhook.py): returns the close on that date or nearest prior trading day (weekend/holiday → `is_estimate=true`). Reuses `_backtest_fetch_prices` (yfinance + CoinGecko fallback, handles crypto suffix). Rejects future dates (400), missing history (404).
- **Honest caveat baked into UI**: close ≠ exact fill (Robinhood fills at live intraday price). Total+date is a *good estimate* (off by intraday drift, usually <1-2%), labelled "· est." when derived from a non-exact day. The exact-price toggle is for anyone who wants precision.
- **What actually needs entry_price**: every %-based alert/nudge (hold-fold, take-profit, EOD % P&L) needs only per-share entry price. Shares ONLY affects dollar figures ($ P&L, "$X at risk"). So the date-lookup's real job is recovering entry price for someone who knows only a total — it is load-bearing, not optional.
- `cmd_market.py /size` and `formatters.py` build_picks_keyboard already use fractional crypto sizing (`round(budget/price, 6)`) — never `max(1, int(...))` which fabricates whole coins.

## Development rules

### Scope — always apply changes everywhere
- When making any change, apply it in ALL relevant places — not just the most obvious one
- For any frontend change, check webhook.py for the matching API endpoint and update it too
- For any API change, check miniapp/index.html for all call sites and update them too
- For any data a page needs on load, ensure it is included in the API response
- After fixing a bug, scan for the same pattern in adjacent code paths and fix those too

### Auto-save / UX
- All form inputs must auto-save on blur — never require a manual Save button as the only save path
- Never call `tg.enableClosingConfirmation()` — always use `tg.disableClosingConfirmation()` + `window.onbeforeunload = null`

### State persistence
- Never use sessionStorage as the sole source of truth for user state — sessionStorage is wiped on app close
- For state that must survive app restarts, piggyback it onto an existing API response (e.g. `_meta.bought_tickers` in picks)
- Live price always trumps stale stored price — use `get_live_price()` for any current price display

### Timing / schedule references
- Morning run cron: `0 11 * * 1-5` = 7:00 AM ET
- All user-facing strings must say 7 AM ET — never 8 AM ET
- **Primary scheduler**: cron-job.org (free) → POST `https://<render-url>/trigger/morning?secret=CRON_SECRET` at 11:00 AM UTC on weekdays. Fires within seconds, reliable.
- **Backup scheduler**: GitHub Actions (`.github/workflows/daily_run.yml`) — still runs all other jobs (confirmation, EOD, alerts, etc.). Morning cron kept as fallback but duplicate-run guard in `/trigger/morning` prevents double-sending.
- GitHub Actions free tier can delay cron jobs by hours during peak load — this is why cron-job.org was added for the morning run
- `CRON_SECRET` env var must be set on Render — include as `?secret=CRON_SECRET` in cron-job.org URL
- Late-delivery guard was removed — picks now always send since cron-job.org fires on time
- **🔴🔴 THERE ARE THREE KEEP-WARM SCHEDULES AND THE IN-PROCESS ONE WINS.** `webhook._keep_alive_loop` pings its own `/health` every 14 min from a daemon thread started at import. Render sets `RENDER_EXTERNAL_URL` automatically, 14 min < the 15 min idle timeout, so **the service never spun down — 24/7, ~744 h/month, regardless of every external schedule.** Narrowing the cron-job.org job and `keepwarm.yml` on Aug 11 changed *nothing* while this thread was alive. It is now gated by `_in_keepwarm_window()` (`KEEPWARM_HOURS_ET`, default `6..13` = 6 AM-2 PM ET). **When the cron-job.org window moves, move `KEEPWARM_HOURS_ET` too — it is the one that actually decides the bill.** Guard: `tests/test_keepwarm_window.py`.

- Always `git add` ALL changed files together — never leave related changes uncommitted
- Provide the full git command (add + commit + push) at the end of every change set

### Read before editing
- Always read the full function/block before modifying it — never edit blindly from grep results alone
- When a bug is in function X, also read all callers of X before deciding the fix
- When adding a field to an API response, read the frontend render function to confirm it actually uses it

### Full data flow verification
- For every change, trace the complete chain: user action → JS handler → API call → Python endpoint → storage → response → JS render
- If any link in that chain is missing or broken, fix the whole chain — not just the link you noticed
- When a feature "doesn't work", check all 5 layers before concluding where the bug is

### Error handling — every async path needs it
- Every `api(...)` call in the frontend must have a try/catch with visible user feedback (toast or inline message)
- Every Python endpoint must handle exceptions and return a meaningful error response, not a 500
- Loading states: every async section must show a spinner/skeleton while fetching and hide it on completion or error

- Every action must give immediate feedback — button state change, haptic, or toast within 200ms

- Empty states must be handled: if a list/section has no data, show a helpful message, not a blank space

### Cache invalidation
- When server data changes (position updated, pick bought, watchlist changed), always call `_invalidatePortfolioCache()` or equivalent and set `loadedTabs[tab] = false` for affected tabs
- Never show stale data after a write — reload the affected tab/section immediately after a successful save

### pandas 2.x compatibility — always use StringIO

- Always wrap response text: `pd.read_html(StringIO(resp.text))` / `pd.read_csv(StringIO(resp.text))`
- When touching any file that calls `pd.read_html` or `pd.read_csv` with response content, grep all call sites and verify they all use `StringIO`
- Every module that makes external HTTP calls and parses the response must have at least one mocked response test

- `scripts/canary.py` is a live-data "fake user" run daily by `.github/workflows/canary.yml` (12:30 UTC) that exercises the whole app AS THE ADMIN and DMs a pass/fail report. - It checks: picks integrity+math, live price sanity (BTC/ETH ranges, CoinGecko cache), sizing math, backtest non-overlap, delivery/cron health (time-aware via `_expected_delivery_date`), `/health`, and MUTATING round-trips (paper buy → entry==per-share-price not the $ total; alert add→replace→remove; watchlist add) each wrapped in **snapshot→act→restore** so the admin's real data is byte-identical after a run.
- **`_check(name, ok, detail, fail_detail=...)`: `detail` is the PASS note (state the fact observed), `fail_detail` is the FAILURE note (state the consequence).** They used to be one field, so a warning-worded note printed on a PASS line — `price_guard` read "plausible_price lets a $0.01/spike through" while green, the exact opposite of what happened. **Rule: never write a canary note as a warning unless it's `fail_detail` (or the check is a hardcoded `ok=False` branch).** Guard: `TestCanaryHelpers` in tests/test_canary.py.

- **Canary checks must tolerate state the synthetic-user bot leaves on the admin account.** Both run on the admin; the synthetic bot holds persistent real+paper positions (ETH, VERX, APD…). A canary check that assumes a CLEAN slate will false-alarm — e.g. `paper.crypto_fractional` bought $200 of ETH and asserted `entry within 2% of live`, but the synthetic bot's pre-existing ETH made `paper_buy` aggregate (correct) so the weighted-avg entry drifted >2%. Fix pattern: assert on the **delta of this action** (shares added ≈ 200/price) and bound aggregates by first principles (a weighted-avg entry always sits between the old entry and the new buy price), NOT `≈ live`. **Rule: any canary check that buys/logs a ticker the synthetic bot might also hold must be delta-based / pre-existing-position-safe, never assume the position starts empty.**

A pick's stop/target are relative to the pick's entry; if the live price has since moved past one, inheriting it blindly creates a position **born already stopped-out** — the next manage run closes it instantly and books a fabricated loss. Seen live: a paper FICO filled at `$1,177.74` carrying the pick's `$1,290` stop. `_levels_for` keeps valid pick levels and otherwise falls back to ±5%/8% of the real fill. Guard: `TestLevelsBracketFill`. **Rule: any code that copies pick levels onto a position filled at a different price must re-validate `stop < fill < target`.**
- **`_save_state` MUST verify the HTTP response and retry.** It was fire-and-forget; GitHub rate-limits (409/403) rapid successive PATCHes to the same gist and a manage run does several writes (close_trade → paper_sell → state × 2 accounts), so a throttled save failed **silently**. Symptom caught live: AMBA was sold on both paths but stayed listed in `synthetic_state_*.json`. Sells self-heal next run (`if not pos: continue`), but on the **open** path a silent failure ORPHANS a live position — the exact bug class the `finally`-persist was added to prevent. Now retries 5× with backoff, returns bool, and the report says `⚠️/🚨 STATE SAVE FAILED`. Guard: `TestStateSaveIsVerified`. **Rule: any Gist write in `scripts/` must check the response — never fire-and-forget.**

### Synthetic trades are TAGGED, never deleted (Aug 3, 2026)

### Score saturation — fixed with a BOUNDED tie-break, not by re-weighting (Aug 9)
- **Measured cause, not assumed**: every component is all-or-nothing and every weight a multiple of 5, so across 400 candidates the ST score took only **19 distinct values**, and the top 20 held just **6 — 14 of 20 were ties**. It was never a cap (the ST score has none; components sum to 195). Ties were then resolved by **whatever order the list happened to be in**, and that arbitrary order decided which names reached Claude and so the user. It also creates cliffs: RSI 54.9 scores 25, RSI 55.1 scores 0.
- **`screener._tiebreak(metrics, strat)` returns [0, 5)** and is added to the base score. Among equally-qualified candidates it prefers stronger signals (deeper into the RSI band, heavier volume, better RS vs SPY) using metrics already computed. Result: **19 → 361 distinct scores, top-20 ties 14 → 0.**
- **🔴 Normalisers must be ASYMPTOTIC, never clamped — learned on the first live run.** v1 used `min(vr/3, 1)`, which saturates at any `vr >= 3`: TWLO (4.03), CART (5.08) and DOCS (9.94) all pinned to 1.0 → identical `4.9` tie-breaks → **TWLO and CART were still tied at 99.9**, i.e. the original defect one level down. It only showed on real data because synthetic frames rarely produced high volume ratios. Now `vr/(vr+3)` and `0.5*(1+tanh(rs/20))` — monotonic, never reaching 1. **Note volume ratio is frequently the ONLY input** (`rs_vs_spy` is None on every live candidate and RSI is usually outside the band), so a ceiling there disables the whole mechanism.
- Precision matters: the tie-break and the total both round to **6 dp**. At 4 dp extreme values rounded back up to exactly 4.9 and re-collided.
- **🔴 THE SAFETY ARGUMENT — this is deliberately NOT tuning.** No weight and no threshold changed. The bonus is bounded BELOW 5, and the smallest gap between two different base scores IS 5, so it is *mathematically incapable* of reordering candidates whose base scores differ. Verified over 160,000 ordered pairs: **0 violations**. It also cannot push a candidate across `ai_analyzer`'s `score >= 50` enrichment gate. Both invariants are tested — **if the tie-break is ever widened to ≥5 those guarantees are void.**
- `metrics["base_score"]` keeps the raw rubric total; **the golden tests pin BASE, not the total**, so "the default rubric is unchanged" is still enforced exactly.
- **`import math` was MISSING at module level and nothing caught it** — `py_compile` passed, `import screener` passed, and every test passed, because the `tanh` branch only runs when `rs_vs_spy` is populated, which it never currently is. It would have raised the first time that metric started working. Guard: `test_math_is_importable_where_the_tiebreak_runs`.
- Fixed en route: a NaN in `rs_vs_spy` passed `isinstance(x, float)` and made the whole SCORE NaN, silently corrupting the ranking — same class as `_is_pos`/`plausible_price`. `_fin()` now rejects NaN/inf/bool.
- Also removed the false **`/100`** denominator from the near-miss line in the morning message; the score has never been out of 100.
- **`_RateLimiter.acquire()` now RETURNS its grant time.** The old test timed itself after acquiring, which under full-suite load measured thread scheduling rather than the limiter and failed spuriously — and a flaky failure here **triggers self-heal, which auto-merges and deploys**. Timing tests in this repo must measure the event, not the observation.

### 🔴 The entry-window promise has ONE definition: `formatters.entry_window_pct()` (Aug 8)
- The morning message says **"Enter within 2% — skip if above $X"**. That number lived in THREE places — `formatters._entry_window` (2%/3%), a hardcoded `gap_pct >= 3.0` in `agent._build_premarket_gap_warnings`, and again in `actionability`. They drifted, and the drift reached users: a SHORT-TERM pick promises 2%, but the gap check only warned above 3%, so a pick could **breach its own published rule in silence**. Measured on live fills — **ANET +2.43% and NWSA +2.15% produced no warning at all**, while the message told users to skip anything above 2%.
- Fix: `formatters.entry_window_pct(is_long_term, is_crypto)` is the ONE source (2.0 / 3.0 percent). `_entry_window` renders from it, the gap check tags each pick with `_window_pct` and warns on `gap_pct > window`, and `actionability` derives its table from it. **Rule: never re-hardcode 2 or 3 for an entry window — import it.**
- Guard: `TestEntryWindowIsOneDefinition`, including a test that the RENDERED line matches the constant (the number a user reads must be the number the code enforces) and one asserting the flat `>= 3.0` cannot come back.

### Actionability — is a pick TRADEABLE, separate from whether it is RIGHT (Aug 8)
- **`actionability.py` + the admin card** answer a question the evaluator cannot: *could a user have acted at the price we published?* Win rate needs ~1,500 observations; these are DESCRIPTIVE, so a few dozen fills already inform. They also separate two failures a win rate conflates: a pick that was **wrong** vs one **stopped out by ordinary noise** — opposite fixes.
- **🔴 First real finding: 3 of 20 picks (15%) filled OUTSIDE the entry window the morning message promises.** COHR published $328.25 → filled $346.15 (**+5.45%** against a 3% long-term promise); ANET +2.43% and NWSA +2.15% against a 2% window. The message says *"skip if above $X"*, so a user who obeyed the instruction would have skipped picks our own bot bought. **That is a trust bug, not a performance one**, and no win rate would ever show it.
- **One observation per PICK, not per fill.** The bot holds the same ticker as both a real and a paper position and both join to one pick; counting both weighted whichever picks it happened to buy twice (31 → 20 observations once deduped). Reachability is a property of the pick.
- Filling BELOW the window is never a breach — a cheaper fill is a better one, only `slippage > window` counts.
- Inverted stops are skipped here rather than counted as 0% — those are an INTEGRITY problem (`position_audit`), and folding them in would drag the median toward nonsense.
- **Exit reason gap — FIXED (Aug 8).** `close_trade` hardcoded `outcome="manual"` for EVERY caller, so the synthetic bot's target/stop sells were indistinguishable from a human clicking sell, and stop-vs-target was unmeasurable. Now `close_trade(..., outcome=...)` validated against `VALID_OUTCOMES = ("manual","target","stop","expired")` — an unknown value falls back to `manual` so free text can never poison an aggregate that groups by it. The bot passes `"target"`/`"stop"`; the Mini App sell flow keeps the default because it genuinely IS a human decision. **Rule: `manual` means a HUMAN chose to sell — never use it as a catch-all, or the reason becomes unmeasurable again.** Guard: `TestExitReasonIsRecorded`, including one test that the bot actually PASSES a reason (the capability existing while the caller ignores it was the original bug).
- Every figure carries its `n`, and a `sample_warning` appears below 30 matched fills.
- **🔴 A closed position must STAY in the denominator.** COHR was the worst breach on record (+5.45% vs a 3% promise); the moment the bot sold it the observation vanished and the headline "improved" 15% → 8.7% with nothing having got better. Two causes: `paper_sell` wrote a history record with `closed_date` only — **dropping `bought_date`, so a sold paper trade had no ledger join key at all** — and `_build_actionability` never passed `paper["history"]` in. Real closes were always fine (they keep `opened_date` + `entry_price`). Fixed at both ends; paper history also carries `stop_loss`/`target_price` now. **Rule: a metric about a PROMISE must not get quieter as trades close — that fails in the flattering direction.**
- **`closed_date` is NEVER a fallback join key.** Joining a sale date to a pick date silently matches the wrong pick whenever a ticker is picked more than once. Rows with no open date are counted as `undated` and reported in the card — an unjoinable breach must be visible, not dropped. The 4 pre-fix history rows (COHR among them) are unrecoverable and show as `undated`.
- `stop_distances` dedupes on `(ticker, open date, entry, stop)` — once history feeds in, a closed paper trade and its former open record are the same position (live n went 40 → 31).

### Position integrity audit + admin worklist (Aug 8) — turning bot data into fixes
- **`position_audit.py`** checks arithmetic that must hold for ANY long position regardless of strategy: `target <= entry` (cannot win), `stop >= entry` (born stopped-out), `target <= stop` (inverted), missing/NaN entry (every %-based alert and P&L is dead), non-positive shares. Found by hand on live data first: **two AMBA positions with target BELOW entry**, and it independently re-found the documented FICO case (fill $1,177.74 carrying the pick's $1,290 stop).

- **🔴 A finding's id must include the LEVELS, not just (check, account, ticker, date).** The bot scales into the same ticker twice in a day routinely (it did exactly that with AMBA on 2026-08-03), and the first version collided — two distinct broken positions became one row, so resolving one silently resolved the other. If a level is later corrected the id changes, which is correct: that is a different finding and the old disposition must not carry over.

### 🔴 Finnhub rate limiting — a semaphore is NOT a rate limit (fixed Aug 8)
- **The live daily prescreener was making 96-98 Finnhub 429s on EVERY run**, leaving **51 of 79 candidates (65%) with no fundamentals at all**. Long-term scoring is ~90% fundamentals (P/E 30, revenue growth 25, net margin 20, debt/equity 15), so LT picks for real users were being chosen largely on *which tickers happened to slip through the limit* — close to arbitrary. This ran unnoticed for as long as the logs go back; it was found only because A/B arms doubled the load and made it obvious.
- **Root cause: `threading.Semaphore(4)` with the comment "stays under 60/min".** A semaphore bounds CONCURRENCY, not RATE — four workers issuing ~100ms requests is ~2,400 calls/min. Demonstrated in a test: the semaphore permits >180,000 calls/min.
- **Fix: `screener._RateLimiter`** — a real token bucket over a rolling window that BLOCKS until a slot frees, applied via `@_finnhub_ratelimited` **beneath `@_memoised`** on all five fetches, so a memo hit costs no budget and no call site can forget it. Cap `_FINNHUB_MAX_PER_MIN = 50` (free tier is 60).
- **Rule: a concurrency bound is not a rate bound.** If an API documents calls-per-minute, the guard must be time-windowed. Guards: `TestFinnhubRateLimit` pins the misconception, the per-window cap, that it does NOT throttle under the cap, and the decorator ORDER.
- Cost: ~278 calls at 50/min ≈ 5.6 min of throttling; prescreener goes ~3 min → ~9 min against a 30 min timeout. If that ever gets tight, the real lever is caching fundamentals across days (they change quarterly), not raising the cap.

### Strategy parameters — the foundation for A/B arms (Aug 8, step 1 of N)
- **`screener.Strategy`** (frozen dataclass) holds every short-term scoring weight/threshold that used to be a hardcoded literal; **`DEFAULT_STRATEGY` IS the live engine** and `run_screener(..., strategy=DEFAULT_STRATEGY)`. All three production callers (agent ×2, run_prescreener) pass no strategy, so real users are served by the default — verify that stays true.
- **🔴 The load-bearing guard is `TestStrategyDefaultsAreUnchanged`**, which pins 12 golden scores captured from the code BEFORE any literal was extracted, plus a field-by-field assertion. Turning weights into config is only safe if the default reproduces the engine exactly; verified a one-point change to `w_rsi` fails 2 tests. **Never "tidy" a default value — that silently changes what real users are recommended.**
- **`STRATEGIES` registry**: `default` / `breakout` (momentum only — `w_rsi=0, w_bb_bounce=0`) / `pullback` (mean-reversion only — `w_breakout=0, w_near_high=0`). Arms are deliberately FAR APART: only picks where arms DISAGREE carry information, so near-identical variants need more data than we will ever have. Guard `test_arms_actually_disagree` requires ≥8/12 differing scores.
- **Why arms at all**: comparing "v1 in July vs v2 in August" measures July vs August. Arms run on the SAME days, removing the regime confound. ### 🔴 pick_ledger is YEAR-SHARDED — a Gist file is unreadable past ~1 MB (Aug 5)
- Picks (~700 KB/yr) + controls (~370 KB/yr) cross the ~1 MB truncation wall **inside one year**. Past it GitHub returns `truncated:true` and partial content, which on the evaluator's swallowing read path looks like an EMPTY ledger — it would re-record every pick ever made.
- **Fix**: `_load_ledger()` merges every `pick_ledger*.json` shard for reads; writes touch only `pick_ledger_{YYYY}.json`. The legacy `pick_ledger.json` is **read-only history and is never rewritten**, so it cannot be clobbered. `record_today(shard, known=...)` dedupes against keys in the OTHER shards, so a year rollover can't re-record a pick.
- **`_save_ledger` VERIFIES the write and retries** (5× backoff, returns bool). It was fire-and-forget, which is worse here than anywhere else in the project: `record_today` only ever reads TODAY's `picks.json`, so a throttled PATCH loses that day's picks **permanently — no later run can backfill them**, and a lost day correlates with the busy morning window, quietly biasing the sample the launch decision rests on. On failure it DMs the owner and **exits non-zero** so the workflow goes red and self-heal sees it. Guard: `TestLedgerSaveIsVerified`.
- `_content(meta)` refetches via `raw_url` when truncated — the same guard as `storage._gist_content`, needed because this script talks to the Gist API directly instead of going through storage.py. **Rule: any NEW script that reads a gist file directly must use the truncation guard, not `meta["content"]`.**

### Self-heal — autonomous fix→merge→deploy on monitor failure (`.github/workflows/self_heal.yml`)

### Loyal users first — every change must be zero-impact on UX
- This app has active users who trust it for real trading decisions. Any change that degrades their experience — slower loads, spinners where there were none, stale data, layout shifts — is unacceptable regardless of how clean the code is.
- Before any backend change: verify the API response shape is identical. Never rename, remove, or reorder fields that the frontend consumes.
- Before any frontend change: ask "does this cause a flash, a re-render, or a spinner that didn't exist before?" If yes, find a way to make it silent (in-place DOM update, background fetch, stale-while-revalidate).
- Performance improvements must not compromise data freshness. Users watching live positions expect prices to be real-time. A cache that makes the tab feel faster but shows a stale price is worse than a slow load with a correct price.
- Decouple structure from data: load stored data (positions, picks, watchlist) instantly, then overlay live prices asynchronously. Never block the render on a live API call.
- Auto-refresh timers must be silent: no spinners, no full re-renders, no innerHTML swaps that reset scroll position. Use targeted DOM updates (getElementById, textContent, style.width).
- If a background job (refresh, sync, price update) fails, swallow the error silently. Never surface a background failure to the user as an error state.
- When in doubt: do less. A conservative change that improves load time by 20% with zero UX risk beats an aggressive change that saves 60% but has a 5% chance of a visible flash.
